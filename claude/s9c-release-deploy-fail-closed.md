# S9C — Fail-closed immutable release deployment

## Context

K'FIT production currently uses four immutable GHCR images (api, client, ops, renderer) and a release manifest generated by GitHub Actions.

Validated release architecture already exists:

- release manifest contains exactly four digest refs;
- production Compose has local fallback image names so local review/build remains possible;
- the backup scheduler already parses /srv/kfit/config/release.env fail-closed and never sources it;
- VPS deployments have been done manually by exporting KFIT\_\*\_IMAGE variables and using --no-build.

A production gotcha is documented in exploration-cache/technical/gotchas.md:
if the image variables are not exported, Compose can resolve kfit-prod-\*:local and a careless command can build/run a local image on the VPS.

This slice removes that operational footgun without changing local development behavior.

## Goal

Add one documented production deployment path that:

1. accepts a GitHub release-manifest JSON;
2. validates it strictly before touching runtime;
3. deploys only the four immutable digest refs from that manifest;
4. never builds application images on the VPS;
5. does not source/eval manifest content;
6. records /srv/kfit/config/release.env only after the selected release has successfully reached the deployment commit point;
7. supports the same mechanism for rollback to a previous manifest.

No business/domain behavior changes.

## Reuse

Reuse the validated S9A.7 backup launcher mechanisms:

- strict allowlist;
- exact repository/image-name matching;
- digest-only refs;
- no arbitrary shell sourcing;
- --pull never where appropriate;
- fail closed on malformed/unknown content.

Reuse the release manifest contract from ops/ci/release-manifest.mjs:

- repository must be fredpatch/kfit-monorepo;
- commit must be 40 lowercase hex;
- compose_env must contain exactly:
  - KFIT_API_IMAGE
  - KFIT_CLIENT_IMAGE
  - KFIT_OPS_IMAGE
  - KFIT_RENDERER_IMAGE
- each ref must be ghcr.io/fredpatch/kfit-monorepo/<kind>@sha256:<64 lowercase hex>.

## Target UX

Preferred host command:

```bash
sudo ops/deploy/kfit-release.sh /srv/kfit/releases/<commit>.json
```

Optional explicit configuration may be supported by environment variables, but defaults must match current Hostinger layout:

- repo: /srv/kfit/app
- runtime env: /srv/kfit/config/.env.prod
- current release env: /srv/kfit/config/release.env
- release archive dir: /srv/kfit/releases

Do not require Node/npm on the host. Ubuntu/POSIX shell + Python 3 + Docker Compose are acceptable.

## Required behavior

### 1. Validate manifest before Docker mutation

Reject before pull/up if:

- file unreadable;
- invalid JSON;
- repository mismatch;
- commit missing/invalid;
- compose_env missing a key;
- compose_env has an extra key;
- wrong image kind under a key;
- tag instead of digest;
- latest/local ref;
- malformed digest;
- whitespace/newline/injection content;
- duplicate/ambiguous data.

Never source or eval the manifest.

### 2. Use a temporary deployment env

Generate a temporary env file from validated manifest data.

Do not overwrite /srv/kfit/config/release.env yet.

Use Docker Compose with that temporary env explicitly, e.g. the equivalent of:

- KFIT_ENV_FILE=/srv/kfit/config/.env.prod
- docker compose --env-file <temporary-release-env> -f docker-compose.prod.yml ...

The helper must not depend on inherited KFIT\_\*\_IMAGE shell variables. Prefer clearing/overriding them so a stale shell cannot change the selected release.

### 3. Pre-deploy resolution check

Before mutation:

- run Compose config;
- resolve images;
- prove api/client/ops/renderer resolve to exactly the four manifest refs;
- prove no application image resolves to kfit-prod-\*:local or a tag.

Postgres/ClamAV fixed third-party images are outside this four-image equality check.

### 4. Pull selected release explicitly

Pull api/client/ops/renderer by the validated digest refs.

No build.

A missing/unpullable image aborts before runtime replacement.

### 5. Deploy with no build

Use the validated temporary env and:

- docker compose up -d --no-build

Do not use a path that can implicitly build an application image.

Preserve existing external runtime env (.env.prod), networks, volumes and profiles.

Mailpit is no longer part of normal runtime and must not be started by this helper.

### 6. Deployment commit point

The durable current-release markers are:

- /srv/kfit/config/release.env
- archived manifest under /srv/kfit/releases/<commit>.json

They must represent the release considered current by operations/backup.

Do not update the current release.env before the deployment reaches the chosen success gate.

Define a practical success gate using existing healthchecks:

- api healthy;
- client healthy;
- renderer healthy;
- postgres healthy;
- clamav healthy.

Do not introduce an application-data test dependency.

After success:

- atomically install/copy the validated manifest under /srv/kfit/releases/<commit>.json if not already there;
- atomically replace /srv/kfit/config/release.env with exactly the four validated image lines;
- preserve safe ownership/permissions suitable for the existing root-owned production config.

If health does not converge:

- exit non-zero;
- do not claim the new release current in release.env;
- print a concise rollback instruction using the previous archived manifest;
- do not silently auto-rollback unless an existing validated project mechanism already supports it.

### 7. Rollback

The exact same helper must accept an older valid four-image S9B+ manifest.

Document rollback as selecting the previous manifest and rerunning the helper.

For manifests from before S9B (three images / Chromium-in-API), reject them in this new production path. They no longer satisfy the current security floor.

### 8. Backup scheduler compatibility

After commit point, existing ops/systemd/kfit-backup.sh must continue reading the four-key release.env unchanged.

Do not weaken its parser.

### 9. Local development remains unchanged

docker-compose.prod.yml may retain local image defaults for explicit local review/build.

The hardening is the production deployment path, not removal of developer convenience.

## Tests / static verification

Add focused packaging tests for the deployment helper. At minimum:

- valid four-image manifest accepted;
- missing renderer rejected;
- extra KFIT_WORKER_IMAGE rejected;
- wrong repository rejected;
- api key pointing to renderer image rejected;
- tag/latest/local ref rejected;
- malformed digest rejected;
- command/injection-looking JSON string cannot execute anything;
- stale inherited KFIT_API_IMAGE cannot override manifest selection;
- helper invokes Compose with --no-build;
- helper never invokes docker compose build;
- release.env is not replaced before simulated health success;
- release.env is atomically replaced after success;
- old three-image manifest rejected;
- backup parser remains green.

Tests must use fake docker/docker-compose behavior; they must not touch a real Docker daemon.

## Out of scope

- deployment UI;
- Kubernetes;
- blue/green infrastructure;
- application migrations redesign;
- real customer/domain data;
- off-server backup provider implementation;
- legal/privacy review;
- S9A.9 acceptance.

7. rollback drill using the same release if a no-op path exists, otherwise previous compatible four-image manifest when available.
